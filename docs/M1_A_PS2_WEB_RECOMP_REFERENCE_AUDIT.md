## 2. Priority architectural investigations

### A. VU0 macro-mode hazards — first Batch 2 correction

**Hardware:** VU manual §5.4.2 (*Macro Mode and the Pipeline*), printed pp.210–211: dependency detection compares the **whole register number** and does not do per-component masks; VF[n] and VI[n] of equal n are regarded as the same *hazard identity* even though they remain **different functional register files**. VF00/VI00 do not cause these scoreboard dependencies. The manual's §5.4.4 describes the extra one-cycle macro operation stall following QMTC2, CTC2 or LQC2; that separate forwarding constraint is **not** corrected by simply merging dependencies. VWAITQ is the explicit Q barrier. Special ACC/Q/P/flag paths require separate identities and are not generic VF/VI register aliases.

**Example:** `QMTC2 r8, vf4` followed by `CFC2 r9, vi4` must encounter same-number macro dependency logic; the reverse `CTC2 r8, vi4` → `QMFC2 r9, vf4` likewise. `QMTC2 r8, vf0` → `QMFC2 r9, vf0` must not induce a false *register-0* hazard. These examples concern the model's dependency classification; exact cycles must come from independent measurements and correct forwarding rules, not an ad hoc stall.

**Observed native behavior:** `c_ee_issue_trace_replay` emits VF or VI masks from the decoder correctly as *functional register types*. `c_ee_issue_timing_probe::issue` currently checks, reserves, and overlaps VF and VI entirely separately; it also includes bit zero. Tests currently codify VF4→VI4 *independence* and VF0→VF0 *stall*, contradicting the manual. Fix the **offline hazard scoreboard**, not actual `m_vu0` contents and not the runtime-wide scheduler. Any Q/ACC/flag, transfer-forwarding and VU0↔EE synchronization costs remain unresolved.

**Reference:** `runtime/src/cop.cpp::cfc2/ctc2` and `runtime/src/vu_micro.cpp::read_q/commit/lower` show actual state and synchronization primitives; they do not provide a plug-in R5900 macro issue scoreboard. PCSX2 can check functional VU0 register read semantics, not establish macro issue timestamps.

### B. COP0 transfer routing, pairing and side effects

**Hardware:** EE Core Table 1-2 maps COP0 operations to logical Pipe 1. Table 1-3 documents combinations where Pipe 0 can issue simultaneously; treating all COP0 transfers as single-issue is an intentionally pessimistic *candidate* rule. EE Core COP0 Count/Compare description (printed pp.70–72) requires a Compare write to remove the timer interrupt request; Status/Cause/EPC and EXL/ERL transitions matter to interrupt acceptability. EE Instruction Set Manual, MTC0 entry, describes necessary SYNC.P ordering after certain writes (EntryHi/TLB exception) and BTAC implications. Do **not** assume a one-cycle general MTC0 penalty.

**Example:** `MTC0 r8, Compare` followed by `MFC0 r9, Cause` should reflect a cleared timer pending state when observed at the architectural boundary; independently, `MTC0 r8, Status` vs adjacent integer operations exercises Pipe 1 pairing. `ERET` changes PC and EXL/ERL, not merely a register dependency.

**Observed native behavior:** `src/llvm/module_builder.cpp` stores MTC0 directly to the CP0 array; `src/lift/native_codegen.cpp` does likewise. `src/runtime/ee_exceptions.cpp` has exception-return, timer tick and interrupt helpers, but the MTC0 emitters do not invoke Compare-clear logic. The LLVM CO path **does** implement ERET/EI/DI, but treats TLB operations as comments/no-ops, so they must not be described as entirely unimplemented COP0. Offline trace replay accepts only explicitly profiled MFC0/MTC0 with `SYSTEM_CONTROL`, rejects ERET/EI/DI/TLB; this is a deliberate timing safety boundary.

**Proposal:** before changing execution, first unit-test a centralized COP0 write hook and examine actual generated LLVM calls. Then use it for Compare interrupt clear, check permissible Status/Cause write masks and interrupt routing from manuals; treat Count progression as unavailable without a validated clock. In parallel, add a *separate offline* COP0 transfer pipe category only once independently verified issue-order evidence exists. Avoid treating host HLE kernel code as a COP0 correctness oracle.

### C. MAC0/MAC1, mixed result deadlines and packed MMI

**Hardware:** EE Core Table 1-2 separates MAC0/Pipe 0 from MAC1/Pipe 1. Table 2-12 distinguishes operation **latency** and **throughput/initiation interval**; MULT, DIV and MADD have different latency and occupancy, but listed values alone do not prove full-program timing. EE Instruction Set MULT1 writes HI1/LO1 (and may write a GPR as defined), independent from HI0/LO0. Packed MMI works on lane-sliced 128-bit registers and requires full-register read/write dependency coverage even where individual lanes remain separate arithmetic values.

**Examples:** `MULT r4,r5` → `MFLO r6` versus `MULT1 r4,r5` → `MFLO1 r6`; two sequential MULT0 operations test whether a later issue may overlap an earlier result, not just what the ALU latency table reports. `PADDW r3,r4,r5` → `PSUBH r7,r3,r8` must record GPR3's complete 128-bit data dependency; a low-64-only reservation is inadequate.

**Observed native behavior:** `c_ee_issue_timing_probe` has distinct MAC0/MAC1 next-issue reservations and HI0/LO0/HI1/LO1 masks. It supports optional conservative WAW and experiment-only ordered overlap (rejecting overtaking or same-cycle completion), *not* validated hardware write ports/forwarding. `mmi_apply` and `emit_mmi_insn` implement many functional packed operations, but `c_ee_issue_trace_replay` deliberately cannot price them. `ps2-web-recomp::now/set_budget` does not establish precise MAC or MMI timing; its *functionality* is useful but its cycle assumptions cannot be transposed to LLVM IR.

**Open evidence gate:** produce independently attributable instruction issue and result-completion traces for both MACs under repeat/RAW/WAW/dual-pipe stress, including cache-miss and branch-slot cases. Existing synthetic `ee_issue_timing_probe_test` and `ee_issue_trace_replay_test` prove software invariants only. Do not install Table 2-12 constants as the native EE clock.

**Justified differences:** LLVM IR modules with stable native calling conventions and explicitly attributed instruction observations should not replicate ps2-web-recomp's generated C unit dispatcher or heuristic host-cycle budget. The current split between guest R3000A execution and HLE IOP kernel is compatible with the reference's philosophy; a wholesale fork/copy would duplicate ownership and make cache/disc state harder to validate. Use ps2-web-recomp as the **primary implementation reference**, Sony as the **hardware specification**, and PCSX2 as a *secondary* functional differential reference.
